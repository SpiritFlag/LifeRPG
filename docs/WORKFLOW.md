# LifeRPG 작업 원칙

2026-10-15 · 사용자와 합의한 프로젝트 조건

## 브랜치와 배포

- 일반적인 조사 결과 반영, 문서 작성, 설계와 개발 작업은 `develop`을 기본 브랜치로 한다.
- `main`은 배포할 때만 사용한다. 배포할 변경을 확정해 `develop`의 작업을 반영한다.
- 일반 작업을 위해 `main`으로 전환하거나 직접 수정하지 않는다.
- 브랜치 사용 원칙만으로 자동 배포나 CI가 설정된 것으로 간주하지 않는다. 실제 연결 방식은 배포 설계에서 정한다.
- 사용자의 최신 선택에 따라 Vercel 배포는 GitHub 연동을 기본으로 한다. `develop`은 검증 배포, `main`은 운영 배포에 사용하며 실제 연동·자동 배포 여부는 확인한 상태만 기록한다. 이 선택은 공개 저장소에 새 코드를 푸시할 승인이나 최종 운영 전환 승인을 대신하지 않는다.

위 항목은 목표와 제약이다. 자원 생성, DNS 변경, 레거시 전환이나 배포의 실행 완료를 뜻하지 않는다.

DB 접근 라이브러리, 검증 도구, MCP 연결 및 OAuth 연계 등 세부 구조는 Astra의 설계안에서 검토한다. 기술 기반의 합의를 구현 착수 승인으로 간주하지 않는다.

## 레거시의 선택과 새 설계

사용자가 전달한 웹 GPT의 철학 정리에는 다음의 구체적인 선택이 담겨 있다. 새 프로젝트에서는 게임의 재미와 단순함, 대화를 오래 멈추지 않는다는 목적을 계승하고, 구현 방식과 수치는 새 설계안에서 검토한다.

| 항목 | 레거시에서 선택했던 내용 |
| --- | --- |
| 실행 | 단일 Vercel 함수와 `waitUntil()`. 별도 Worker 서비스·복구 Cron·새 큐·메시지 브로커를 만들지 않는 방향 |
| 대기 | 기본 15초 안에 완료하면 같은 MCP 호출로 결과 반환, 초과하면 처리 중 안내 후 저장 결과 조회 |
| 예산 | 운영 기준 월 $10 |
| 모델 설정 | `gpt-6.1-sol`, reasoning Medium, 출력 상한 16,384토큰 |

이 표는 당시의 선택을 보존한다. 새 자원 구성이나 유료 실행의 승인, 새 서비스의 적용 완료를 뜻하지 않는다.

## 협업

사용자와 원청 개발 담당자가 목적, 원하는 경험, 중요한 제약을 함께 정한다. 자유로운 논의를 곧바로 구현 지시로 전환하지 않는다.

코드 조사나 전문적인 설계가 필요하면 원청 담당자가 Orca orchestration을 통해 Astra Extra High 개발 총괄에게 의뢰한다. Astra는 `contractor-lead` 임무수첩을 읽고 기술 설계와 워커 운영을 맡는다. 개발·검수 담당은 Sol Medium 워커를 사용하며 독립 검수 역할을 구분한다.

사용자와 설계안을 검토하고 승인한 뒤 구현에 착수한다. 승인된 범위 안에서 Astra가 팀을 운영하며, 범위나 근본 방향이 달라지는 결정은 사용자와 상의한다. 납품 결과를 함께 확인하고 인수와 후속 방향은 사용자가 정한다.

총괄의 납품 후에는 사용자 요청에 따라 세션을 유지해 검토·인수와 다음 지시를 기다린다. 해당 Dispatch의 완료 보고는 한 번으로 끝내고, 후속 지시 전에는 새 작업을 자율적으로 시작하지 않는다.

2026-10-15 사용자는 `66967f2` 설계를 전달받고 구현 착수를 승인했다. 실연결 API 실험은 전체 팀 누적 $3 이내, 운영 API는 월 $15 상한이며 실패 응답 암호화·24시간 접근 기한·후속 정리도 승인 범위다. 신규 유료 요금제나 구독·상한 증액·유료 이미지 생성은 포함하지 않는다. 신규 무료 자원과 개발 검증 배포를 준비할 수 있으며, 최종 운영 배포·도메인 전환·레거시 중지나 삭제는 실제 검증과 되돌릴 수단을 갖춘 뒤 원청에 마지막 전환 판단을 넘긴다.

## 문서

- `DESIGN.md`: 사용자와 함께 다듬는 제품 의도와 설계 공간이다. 현재는 WHAT 초안을 담는다.
- `SPEC.md`: 실제 코드와 동작에 근거해 관리할 기술 명세다. 구현 전에 레거시 스펙을 복사해 새 프로젝트의 현재 동작으로 기록하지 않는다.
- `docs/WORKFLOW.md`: 합의한 기술 기반과 작업 원칙을 보존한다.
- README는 사용자의 영역이며 명시적 요청 없이 작성하거나 수정하지 않는다.

## 품질과 전달

실제 사용 흐름을 끝까지 확인하고 실패를 추적할 근거를 함께 갖춘다. 테스트는 위험과 영향에 맞게 선택하며, 실제 모델 연결의 확인 결과와 mock 검증을 구분한다. 테스트 수를 늘리는 것으로 실제 오류 조사와 연결 검증을 대신하지 않는다.

개인이 즐기는 게임에 맞는 복잡도를 유지한다. 외부 장애나 드문 데이터·비용 손실 가능성을 모두 제거하려고 과도한 복구 장치를 추가하지 않는다. 기본적인 오류 진단은 갖추고, 추가 복구 기능은 실제 필요와 합의한 범위에 따라 판단한다. 비용 관리도 창작의 재미와 개발의 단순함을 함께 고려한다.

새로운 결제·구독·비용 발생, 되돌리기 어려운 파괴적 작업, 외부 공개는 사용자의 승인 범위를 확인한다. 결과는 실행한 사실과 남은 한계를 구분해서 보고한다.
